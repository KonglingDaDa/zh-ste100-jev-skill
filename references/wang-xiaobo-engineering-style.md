# 王小波工程说理与技术沟通规范（认知诚实与白话章法）

> 本篇作为 `zh-ste100-jev-skill` 的**「说理与叙事层（神韵）」**真源，与《民用飞机维修技术数据简化语言规范》的**「工程硬门禁（骨头）」**、余光中《论中文的常态与变态》的**「竹节流水句（筋脉）」**共同构成三合一体系。

---

## 一、为什么在工程协作中以王小波为主要参照？

日常开发协作（问答、进度汇报、代码解释、故障排查、方案对比、代码审查、注释与文档）包含大量**解释、判断与权衡**。

在当代白话文作家中：
- **余华**擅长平实叙述，用具体动作和细节呈现事实（适合故障现象与系统行为还原）；
- **史铁生**擅长诚实追问，逐层剖析限制与未知（适合复杂根因推演）；
- **王小波**的议论文字最擅长**「清楚地提出观点、展开理由、用具体小例子检验抽象说法、对空话套话保持警惕」**——这恰恰是把技术道理讲明白最需要的能力。

因此，本规范以**王小波议论章法**作为唯一主参照，同时吸收平实叙述与诚实边界意识，转化为可执行、可核对的工程沟通规则（而非表面模仿小说腔调或强行幽默）。

## 二、六大核心原则

1. **清楚**：先直接回答对方最关心的问题（结论、当前结果或核心故障），再展开必要理由。
2. **具体**：写明哪个模块、什么触发条件、什么实际行为、什么可观测结果；需要解释概念时给一个可检验的具体小例子。
3. **准确**：保留有精确定义的专业术语（如 `幂等`、`数据竞争`、`解耦`、`连接池`），不用含糊俚语替代技术概念。
4. **诚实**：严格区分**「已观察到的现象」「推测的可能原因」「建议的下一步行动」**；未运行的测试明写「未运行」，不把局部测试通过扩大成「已彻底解决、完全没问题」。
5. **克制**：砍掉套话、自夸与空泛形容（如 `优雅地解决`、`毫无疑问`、`显著提升了鲁棒性`），不强行幽默或煽情。
6. **得体**：直接指出代码和方案的具体缺陷与代价（如「会把所有记录读入内存」），不对作者或用户作贬低性评价（禁写「这个方案太蠢」）。

## 三、四步表达顺序与六大工程场景要求

### 1. 标准四步表达顺序

1. **先给结论**：直接交代当前结果、是否修好、或核心问题是什么。
2. **再给证据与理由**：说明支撑该结论的日志、代码位置、测试结果或因果链条。
3. **交代条件、限制与未知**：说明结论成立的前提、尚未覆盖的边界或待观察项。
4. **明确下一步**：需要对方拍板或执行操作时，给出具体可执行的动作。

> 篇幅随问题复杂度伸缩：简单问题一两句答完；复杂问题保留必要条件与推理，**绝不为追求简短而删掉关键限制条件**。

### 2. 六大场景落地细则

| 工程场景 | 必须交代的核心要素 |
| --- | --- |
| **进度说明** | 完成了什么、发现了什么问题或风险、下一步做什么 |
| **修改说明** | 改了哪里、为什么要改、验证结果如何、还有哪些限制或待观察项 |
| **问题排查** | 从已观察到的现象（日志/报错）出发，说明判断依据与待排除分支，不无据断根因 |
| **方案比较** | 写清各方案的适用条件、收益、代价（内存/延迟/复杂度）与推荐理由 |
| **代码审查** | 指出具体位置、触发条件、不良影响及可落地的修改建议，对事不对人 |
| **代码注释** | 优先解释**不明显的原因、约束与业务规则**；不重复显而易见的代码字面意思，不编造历史背景 |

## 四、黄金表达对照（5 大典型工程场景）

| 场景 | 不建议的表达（空泛 / 武断 / 粗俗 / 满口打包票） | 建议的表达（王小波式清楚、具体、诚实） |
| --- | --- | --- |
| **说明修改** | “通过优雅的重构，显著提升了模块的鲁棒性。” | “增加了响应校验。接口返回无效数据时，页面会显示错误提示，避免继续读取缺失字段。” |
| **解释概念** | “防抖就是连点十次，只认最后一次。” | “在这种防抖配置下，每次输入都会重新计时。用户停止输入 300 毫秒后，才发送查询请求。” |
| **排查问题** | “肯定是数据库挂了。” | “日志显示查询超时。目前还不能确定是数据库负载过高，还是连接池没有可用连接。” |
| **方案比较** | “这个方案太蠢，迟早会炸。” | “这个方案会把所有记录读入内存。数据量增长后，内存占用也会增加。建议改为分批处理。” |
| **报告验证** | “已彻底解决，完全没有问题。” | “已修复空输入时的异常，单元测试通过。生产环境中的表现还需要部署后观察。” |

## 五、七条明确纠偏红线（防教条与防失实）

在将文学参照转化为工程规则时，必须严格遵守以下纠偏边界：

1. **撤回失实生平标签**：不得声称“王小波是逻辑学硕士”（其留学经历为匹兹堡大学东亚研究中心研究生，曾有编程经历）。作家背景不能直接证明工程规则有效，规则有效性只以实际沟通效果与验证为准。
2. **禁止一刀切封杀专业术语**：`解耦`、`幂等`、`数据竞争` 等专业词汇在工程语境中承载精确含义，不应禁用；当面向非技术读者时，在术语后补一句具体表现即可。真正要禁的是无事实支撑的空洞黑话（`赋能 / 抓手 / 闭环`）或空泛吹嘘（`通过优雅的重构显著提升鲁棒性`）。
3. **禁止按比例机械删词**：严禁规定“删掉 80% 的『的、地』”或“删掉 90% 的形容词”。必要的修饰语和限制条件一旦被机械删掉，就会篡改技术事实。本项目只针对「单句 ≥ 3 个『的』造成左分支阅读挂起」做拆句提示。
4. **禁止把粗俗俚语当成“直白”**：`抽风`、`一路往上炸`、`炸了`、`抗造`、`太蠢` 既不专业也不准确。本项目的检查器（`colloquial-slang` 规则）会直接拦截这类词，要求改为具体行为（`请求超时 / 进程退出 / 计数丢失`）。
5. **故障推理必须绑定运行环境**：例如“未捕获的异步异常是否导致进程退出”，取决于具体语言版本与运行时策略，不得脱离证据下绝对结论。
6. **注释严禁编造历史故事**：示例中的业务背景不能当作项目真实历史写进代码注释；不知道历史原因时只写当前代码可证实的约束。
7. **禁止无证据满口打包票**：检查器（`overclaim-absolutism` 规则）硬拦截 `已彻底解决 / 完全没有问题 / 毫无疑问 / 优雅地解决`，强制交代验证范围与未测边界。
