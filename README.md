# `zh-ste100-skill` — 中文受控技术与汇报写作技能（软硬双引擎）

> **用中国民机手册的「硬信息门禁」锁死事实与确定性，用汉语言文学的「竹节流水句」治好 AI 翻译腔。**
>
> 专治中文 AI 任务报告、技术文档与排障说明**「每个字都认识，但串在一起不知道在说什么，且满篇打太极」**的顽疾。

---

## 为什么英文有 ASD-STE100，中文却需要一套「软硬结合」的新规范？

航空工业的 **ASD-STE100（简化技术英语）** 是为了让飞机维修工不可能读错指令而设计的受控自然语言（Controlled Natural Language）。但把英文 STE100 直接翻译成中文会水土不服——因为**中文读不懂的病因和英文完全不同**：

| 病因维度 | 英语的歧义来源 | 中文（尤其 AI 报告）的四大崩坏病灶 | 本项目「软硬双引擎」解法 |
| :--- | :--- | :--- | :--- |
| **1. 句法结构（软）** | 从句挂在名词后面（右分支），挂接歧义 | **左分支「的的不休」**：把条件、原因、路径全塞进名词前的「的」字串里，读者读了 40 个字还没见到核心动词，短期工作记忆直接挂死 | **现代汉语「竹节流水句」**（`de-stacking`）：单句最多 2 个「的」，按「前提 → 谁+真动词 → 结果」拆成短句顺流而下 |
| **2. 动词筋骨（硬+软）** | 短语动词（Phrasal verbs）一词多义 | **弱动词与名词化（文字的义肢）**：余光中《论中文的常态与变态》痛批的西化病——把真动词冻成抽象名词，再用 `对…进行/作出/加以/予以/完成对…的` 拼凑 | **真动词直写**（`nominalization`）：提供 6 大域核心单/双音节真动词表，硬拦截一切弱动词套壳 |
| **3. 语序外壳（软）** | 介词短语与被动语态泛滥 | **欧化介词套壳 + 分号焊长句**：动辄 `基于…的情况下 / 针对…的问题 / 对于…而言`，再用分号或 `并且/同时/从而` 把三件事焊成一句 | **剥壳 + 一句一事**（`translationese-shell` / `semicolon-join`）：删掉介词壳，禁用分号串动作 |
| **4. 结论确定性（硬）** | 情态动词模糊责任 | **太极推诿词 + 黑话糊弄**：满篇 `应该、大概、基本上、理论上、似乎、在一定程度上` 和 `赋能、闭环、抓手、收口、对齐、最小侵入式` | **确定性铁律**（`taichi-hedge` / `jargon-buzzword`）：首句给死结论，已验证与未验证显式二分，硬拦太极词与黑话 |

## 核心设计：三档运行模式（Three Modes）

借鉴中国商飞等起草的**《民用飞机维修技术数据简化语言规范》/ GB/T 42852-2023** 将手册分为「程序步骤」与「描述性内容」的工程思想，并针对 AI 协作专门增设**「任务汇报档（`report`）」**：

1. **`report`（任务汇报档，默认）** —— 面向 AI 对用户的回复、任务完成汇报、故障排查结论、PR 总结
   - **单句上限 ≤ 35 字**；
   - **首句给死判断**（成了 / 没成 / 卡在哪 / 原因是什么）；
   - **硬拦太极词**（`应该/大概/基本上/理论上/似乎/在一定程度上`）；
   - **已验证 vs 未验证显式二分**（例：`单测 6 条全过；浏览器登录尚未联调`）。
2. **`procedure`（操作指令档）** —— 面向部署步骤、运维 Runbook、排障操作、Agent 派工 brief
   - **单句上限 ≤ 25 字**；
   - **一步一动作**，条件与致命风险必须写在动作前面；
   - 明确区分「人工操作」与「系统自动行为」，禁用分号串联。
3. **`descriptive`（技术说明档）** —— 面向 README、架构说明、API 概念、工具与函数描述
   - **单句上限 ≤ 40 字**，一段一主题（≤ 6 句）；
   - 去虚动词、去黑话、去长定语，保留客观情态词。

## 一眼看懂：改写前后对比

### 场景 1：AI 任务完成汇报（`--mode report`）

- ❌ **原始病句（89 字单句、3 层介词壳、3 个“的”、弱动词、黑话、太极词）**
  > 需要注意的是，本次针对网关鉴权链路在缺少会话凭证的情况下可能会引发未授权穿透的相关风险问题，已经通过最小侵入式的方式完成了对中间件的边界收口与逻辑对齐；目前整体功能基本上应该已经恢复正常了。
- ✅ **软硬双引擎改写后（竹节短句 + 死结论 + 已验/未验二分）**
  > 网关鉴权中间件已修复，缺少 Cookie 的请求现在直接返回 401。我只修改了 `auth.ts` 的 12 行验证代码。单元测试 6 条全部通过，浏览器端登录尚未联调。

### 场景 2：运维与航空手册操作指令（`--mode procedure`）

- ❌ **原始病句（致命警告塞在句末括号、分号串动作、弱动词）**
  > 在对生产环境的二进制文件进行替换之前需要确认备份目录权限正确；接着把新版本复制过去并重启守护进程（注意如果哈希校验不一致千万不要执行替换操作）。
- ✅ **软硬双引擎改写后（风险置顶 + 一步一动作 + ≤25 字）**
  > 警告：新二进制文件的 SHA-256 验证未通过时，禁止替换生产文件。
  > 1. 确认备份目录权限为 `700`。
  > 2. 验证新二进制文件的 SHA-256 值。
  > 3. 将新二进制文件复制到 `~/.local/bin/`。
  > 4. 重启守护进程。

## 快速开始与工具链用法

### 1. 运行内置自检与全量测试（零依赖，仅需 Python 3.10+）

```bash
# 运行静态检查器内置自检
python3 scripts/zh-ste-lint.py --selftest

# 运行可选 Jev 语义复核器离线自检
python3 scripts/zh-ste-jev.py --selftest

# 运行全量单元测试
python3 -m unittest discover -s tests -v
```

### 2. 检查 Markdown 或汇报文本（`scripts/zh-ste-lint.py`）

```bash
# 按任务汇报档（默认 --mode report，单句上限 35 字）检查文件
python3 scripts/zh-ste-lint.py examples/after-only.md

# 按操作指令档（--mode procedure，单句上限 25 字）检查
python3 scripts/zh-ste-lint.py --mode procedure your-runbook.md

# 从标准输入直接检查一段 AI 回复，并输出结构化 JSON（契约版本 zh-ste100/v1）
echo "需要注意的是，已经对相关配置进行了最小侵入式收口；基本上应该好了。" \
  | python3 scripts/zh-ste-lint.py --mode report --json

# 列出全部 13 条软硬检查规则
python3 scripts/zh-ste-lint.py --list-rules
```

退出码约定：
- `0`：硬违规数（`advisory-free`）`<= --baseline`（默认 `0`）；
- `1`：硬违规数超出基线；
- `2`：命令行参数或文件路径错误。

### 3. 可选：运行 Jev（System One）语义复核（`scripts/zh-ste-jev.py`）

当本机或环境配置了 TypeSafe Jev 网关（`TYPESAFE_BASE_URL` 默认 `http://127.0.0.1:18650` + `TYPESAFE_API_KEY`）时，可对静态门禁通过后的文本做百毫秒级语义判断（首句结论确定性、无太极推诿、竹节句自然度、原意保真度）：

```bash
python3 scripts/zh-ste-jev.py \
  --mode report \
  --file examples/after-only.md \
  --original examples/before-after.md \
  --json
```

未配置 `TYPESAFE_API_KEY` 时，脚本自动返回 `status="unavailable", verdict="skipped"`（退出码 `0`），不阻塞离线使用。
